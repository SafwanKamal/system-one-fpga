# v9i board pilot and v9k feasibility (2026-11-23)

Coordinator run `d3f06adaeb92` (Claude, Codex and Gemini), integrated from the reviewed tips:
Claude `2570aaf`, Codex `d2f43ee`, Gemini `c53def5a`.

## Summary

- **v9i is bit-exact on hardware.** In the pilot, all 57 compared outputs matched RC1.3 / v9h.
- **v9i is 1.28x faster end-to-end on the service's tool queries.** The model predicted 1.31x.
- **v9i is slower on long prompts:** prefill is 0.89x there, because P=2 attention costs more at
  long positions.
- The analyser's pooled gate says **NO-GO**. Making RC1.4 the default service is a trade-off, and
  it needs the user's approval.
- **v9k (prefill batch 16) does not fit the K26.** Its memory is the blocker, and the gain would be
  small anyway. Do not route it.

## v9i (RC1.4) pilot

Full record: `experiments/v9i/pilot/RESULTS.md` (Gemini-reviewed; analyser output reproduced byte
for byte).

| | Result |
|---|---|
| Identity | **57/57**: 21 tool queries token-identical to RC1.3; 36 raw cases identical in tokens, FP32 logit bits and K/V SHA-256 (both arms) |
| Service bench, end-to-end | 23.46 → 18.32 s, **1.28x** (prefill 1.38x, decode 1.21x) |
| Raw prefill by domain | tool 1.45x, general 1.16x, maintenance 1.08x, **long 0.89x** |
| Raw plain decode | 1.00x (unchanged path) |
| Raw drafted decode | 0.90x, with v9h's P=4-tuned qualification drafter, not the RC1.4 drafter |
| Analyser gate (pooled 57) | NO-GO: decode 0.918x, end-to-end 1.003x (thresholds 1.03x / 1.00x) |
| Board after pilot | RC1.3 restored on the same boot, v9h, READY, `rc1.3-costaware`; ledger recorded and released |

**Recommendation.**
- **Today's service traffic is tool queries.** For that traffic, RC1.4 is a clean 1.28x win with
  identical outputs, and it would be worth making the default.
- **Hold if long prompts matter.** The cost is about 11% more prefill time on prompts of tens of
  seconds.
- **Two follow-ups would settle it:**
  1. Fit the drafter on v9i board timings. The current coefficients are modelled, and the raw
     check shows the P=4 drafter mispricing v9i.
  2. Measure the RC1.4 service drafter on a long-prompt workload. The raw check does not exercise
     it.
- Promotion to default, like any image change, needs the user's approval.

**Process fix.** PILOT.md's raw-check step now runs `stop` and `up` in the foreground and launches
the check with `systemd-run`. The original instructions, run detached over SSH, left the FPGA with
no app loaded until it was recovered by hand. RESULTS.md has the incident log.

## v9k: prefill batch 16 on v9i (Codex, Claude-reviewed)

| | v9i B=8 | v9k B=16 | K26 |
|---|---:|---:|---:|
| HLS LUT | 137,955 | 181,088 | |
| Routed LUT estimate (with shell) | 92,728 (measured) | ≈ 120,000 | 117,120 |
| BRAM36 equivalents (HLS) | 117 | **194** | 144 |
| URAM | 40 | **68** | 64 |
| Modelled prefill per tool query | 0.391 s (board: 0.408 s) | 0.298 s | |

- **v9k does not fit.** BRAM and URAM are both over capacity, and LUT is borderline. The doubled
  activation banks (15 URAM each) and the matvec slot state (+39.8k LUT, +390 DSP) drive the growth.
- **The gain would be small.** B=16 would save only 0.093 s of prefill per tool query beyond v9i.
  The cost model behind that estimate is now validated on the board: it predicted 0.391 s for v9i,
  and the pilot measured 0.408 s.
- **Exactness C-sim skipped** because v9k does not fit. Gemini's harness now supports `--batch 16`
  (`experiments/attn_reclaim/audit/`, Codex pass after three fix rounds). It includes per-position
  cross-batch comparison, a cache key over the prompt fixture, and isolation for runs that overlap.
- **Recommendation: do not route v9k.** A B=12 variant might fit, but it would save about 0.05 s
  per query. It is not worth a route and C-sim cycle compared with the drafter refit above.
