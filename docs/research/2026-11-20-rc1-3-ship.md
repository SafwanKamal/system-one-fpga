# RC1.3: v9h image with a v9h-calibrated cost-aware drafter (shipped 2026-11-20)

RC1.3 is the default `sysone-rc1.service` on the KR260 as of 19:32Z on 2026-11-20 (boot 62097330).
It is RC1.2 with two changes:

- **Image: v9h instead of v9g.** Passes of up to 4 tokens (single steps and short verify
  passes) split their weight rows across a second HP port, so plain decode is 1.50x faster
  than on v9g. Outputs are bit-exact: the board pilot matched 37/37 cases in both plain and
  speculative modes (`2026-11-19-dual-weight-port-study.md`).
- **Drafter costs refitted on v9h.**
  - Fit: 74 board runs from the v9h pilot. The exact replay first reproduced the board's
    drafting statistics in every case (`experiments/rc13/fit_v9h.py` → `build/v2/rc1-3/fit.json`).
  - Model shape: on v9h a pass of more than 4 tokens loses the split, so the per-pass constant
    splits in two, giving 7 coefficients instead of 6. Worst-case error per run is 2.6%;
    v9g's 6-coefficient form was off by up to 35%.
  - Typical pass costs at position 600: 4 tokens 0.17 s; 5–8 tokens 0.29–0.31 s; a single
    step 0.15 s.
  - Modelled over all 181 cases, the refit makes speculation 12% faster than keeping v9g's
    costs on v9h. That gives about 3.37x over plain v9g; RC1.2 measured 2.58x.

## Operation

- **Bundle:** `/var/lib/sysone/rc1-3-v1`, built from `firmware/rc1_3` by
  `scripts/v2/package_rc13.py` (`rc13.tar`, sha e0039f11...).
- **Drop-ins:** `20-rc13.conf` sits on top of RC1.1's `10-speculation.conf`. Enabling RC1.3
  moves RC1.2's `20-rc12.conf` to `/var/lib/sysone/qualifications/rc1-3/rc12-dropin`.
- **Disable:** `install_rc13.py disable` stops the service under RC1.3, which switches the
  image back to v9e, then restores the RC1.2 drop-in and starts RC1.2.
  - Rollback drill passed: RC1.2 came back with probe `rc1.2-costaware`, and re-enabling
    brought RC1.3 back with probe `rc1.3-costaware`.
- **Images:** v9e stays the resting image. The image log
  (`/var/lib/sysone/qualifications/rc1-3/image.jsonl`) records every switch; each one left the
  DMA residency table unchanged.

## Update 2026-11-20: shared system-template prefix cache and reboot test

### Where prefill time goes

A per-case fit over all 181 v9g pilot cases has a worst-case error of 1.9%. It also predicts
the bench's measured prefill (26.2 s modelled vs 26.0 s measured).

- **Fixed cost per group:** each 8-token prefill group costs 0.166 s, which is one full weight
  pass on one port.
- **Attention cost:** on top of that, each group adds 1.64e-4 s per position (37% of group
  cost at position 600).
- **Bandwidth-bound:** prefill is limited by weight bandwidth. v9h's second port can't help,
  because 8-token passes would need the full dual port.

The larger cost was in the service:

- **Cache cleared per conversation:** the RC1 prefix cache was cleared whenever
  `conversation_id` changed.
- **Effect:** every tool query re-processed the same 38-token system template. Each tool
  prompt is 52–60 tokens and starts with it.

### Change

`spec_service_rc13.py` now behaves as follows on a new conversation without `reset_cache`:

- **What is kept:** only the cached rows of the public system template. That's the common
  prefix of prompts built from unrelated queries, computed at startup.
- **How much is reused:** after rounding down to whole 8-token groups, the first 32 tokens.
- **What is not shared:** no user text from another conversation is ever reused.
- **Explicit reset:** `reset_cache=True` still clears everything.
- **Exactness:** reused rows have the same tokens at the same positions and group boundaries.

The bundle was updated in place with the new `install_rc13.py update`. It backs up the current
bundle files, restarts, probes, and restores the backup if the probe fails. The first attempt
failed its own self-check and rolled back as designed, because the manifest wasn't copied. That
is fixed.

### Reboot test: PASS

- **Boot:** a normal `systemctl reboot` gave new boot `d65e03c2`.
- **Auto-start:** the boot initializer loaded v9e and sealed the model. The RC1.3 unit then
  started by itself, switched v9e → v9h at 19:43:27, and was READY at 19:43:32 with startup
  weights verified.
- **After-boot bench:** 21/21 identical. The first query started with an empty cache; the rest
  reused the template.
- **SSH timing:** logins are accepted about 90 s after the reboot, but command channels can
  time out until startup settles.
