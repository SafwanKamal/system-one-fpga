# v9i full-decoder exactness vs v9h (2026-11-22)

**PASS. v9i is bit-exact with v9h** across all 28 layers in prefill mode: 0 of 1,400,880 compared
words differ, and no NaN reached the K/V cache.

| Field | Words compared | Differing |
|---|---:|---:|
| hidden (after every layer) | 688,128 | 0 |
| kv (packed BF16 cache rows) | 688,128 | 0 |
| norm (final RMSNorm) | 24,576 | 0 |
| token (greedy winner, first 8,192 rows) | 24 | 0 |
| logit (winner's FP32 bits) | 24 | 0 |

Verdict JSON: `experiments/v9i/exactness-prefill.json`.

## What was run

- **Designs:**
  - Baseline: v9h, `build/v2/dual-port-study/src-s2`, source hash `b6d301bd…c135`.
  - Variant: v9i, `build/v2/v9i/src`, hash `225fb69e…87d0`, generated by `make_v9i.py`.
- **Harness:** Gemini's harness, `experiments/attn_reclaim/audit/`. Both ports are driven with the
  same model buffer.
- **Mode:** prefill with `--no-tile-cross`:
  - the K/V cache starts poisoned with BF16 NaN;
  - positions 0–23 run as 3 batch-8 groups;
  - inputs are the Qwen3-0.6B Q8_0 model and the schedule-invariance prompt.
- **Why prefill:** a batch-8 pass is where P=2 differs from P=4. P=2 makes 4 sweeps of the on-chip
  K/V tile per pass, where P=4 makes 2. Decode mode, with one token per pass, would not exercise the
  change.
- **Wall time:** C-sim loop 4,204 s for v9h and 4,631 s for v9i, about 2.5 h in total.
- **Harness fix used for this run:** the published harness launches Vitis from the OneDrive
  checkout path, and its spaces break the C-sim makefile. This run used a scratch copy patched to
  launch from the `S:` drive path (`cwd=run_rel_drive`). Gemini publishes the same fix in this run.

## Coverage limits

- **Tile boundary not crossed in the full decoder.** The 256-row tile boundary is covered only by
  the attention-only probe (`audit/evidence/attention-kernel-verdicts.json`): 75,776 FP32 outputs,
  0 differences, including P=2 across `TILE=256`.
- **Decode mode not run.** Single-token passes use the same code path as before the P change.
- **C-sim only.** This proves source-level equivalence under x86 float arithmetic. Hardware uses
  the same Xilinx floating-point operators in the same order, so the board should match too. A board
  pilot would confirm it on the 21 tool queries, which needs the user's approval.
